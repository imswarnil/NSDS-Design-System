## 0. The one-paragraph version

This is a **mature and unusually well-reasoned system** — the CSS carries real
architectural argument in its comments, the token layer is genuine, and there
are six build-time checks enforcing rules most design systems only write down.
It is not disorganised. What it has is **three separate taxonomies that no
longer line up** (CSS files, React folders, docs families), **one large piece of
true duplication** (template markup copied into the docs generator), and a
**long tail of things that were built and never wired up** (171 dead classes,
28 orphan templates). None of that is a rewrite. It is roughly four batches of
consolidation plus the governance to stop it recurring.

**Top five, in the order I would fix them:**

| # | Issue | Evidence | Risk if left |
|---|---|---|---|
| 1 | Template markup is duplicated verbatim into `component-docs.mjs` | 41 of 52 templates overlap; `course-detail.html` shares 44 long lines | Docs silently drift from shipped markup. Already happening. |
| 2 | Three taxonomies disagree | 23 CSS files have no matching React folder; 4 folders have no CSS | Nobody can predict where a new thing goes |
| 3 | 171 CSS classes defined but never rendered | `training.css` alone has 61, incl. an entire `.ns-gate` subsystem | Dead weight in the bundle; undocumented features nobody knows exist |
| 4 | 28 templates unreferenced by any build | `account.html`, `pagination.html`, `tree.html`, … | Unverified markup that ships in the npm package |
| 5 | React file granularity is inconsistent | `core` = 17 files/18 components; `navigation` = 2 files/22 components | Import paths are unguessable |

### How the layers actually relate

```
tokens.json ──build-tokens──> tokens/*.css ──┐
                                             ├──build-css──> dist/*.css
components/css/index.css ─(33 @imports)──────┘
                    ▲                    ▲
                    │ class contract     │ class contract
        templates/*.html          components/*/*.jsx
        (Ghost, static)           (Next.js LMS)
                    ▲                    ▲
                    └── scripts/component-docs.mjs (markup RE-TYPED here)
                                  │
                          build-preview ──> preview/ ──build-site──> _site/
```

**The critical observation:** `components/css/` is the design system. The React
folders and the HTML templates are *two consumers* of it, and
`component-docs.mjs` is a *third* — which re-types the markup by hand rather
than importing it. That third consumer is issue #1.

## 3. Duplication & repetition

### 3.1 🔴 Template markup re-typed into the docs generator — **the big one**

`scripts/component-docs.mjs` (6,214 lines, 61% of all script code) contains
hand-written HTML for 138 documented entries. Much of it is the *same markup*
that lives in `templates/*.html`, typed a second time.

| Template | Long lines shared verbatim with the docs |
|---|---|
| `course-detail.html` | 44 of 181 |
| `course-player.html` | 43 of 133 |
| `navbar.html` | 41 of 61 |
| `course-player-article.html` | 40 of 155 |
| `ai-chat.html` | 35 of 57 |
| `deck.html` | 30 of 159 |
| `blog-post-ads.html` | 24 of 66 |
| `blog-post.html` | 23 of 46 |
| …and 33 more | |

**41 of 52 templates have verbatim overlap.**

*Why it matters:* these are two hand-maintained copies with no check binding
them. Change a template and the docs keep showing the old markup — which is
exactly what happened repeatedly during this session's player work. `navbar.html`
is the worst case: two thirds of it exists twice.

**Recommended single source of truth:** the template. The docs generator should
*read* `templates/*.html` (it already does this for the full-page demos via
`fragment()`) and extract named regions, rather than re-declaring markup.

### 3.2 🟠 Three overlapping monetization vocabularies

| Concept | Where | Classes |
|---|---|---|
| Third-party ad slot | `ads.css` | `.ns-ad` + 34 |
| Native sponsor card | `monetization.css` | `.ns-sponsor` + 11 |
| Dashed placeholder | `catalog.css` | `.ns-adslot` + 1 |

`ads.css` opens by explaining it is *not* the sponsor card, so the split is
deliberate and argued. But **both** define `--leaderboard`, `--skyscraper`,
`--square` and `--article` modifiers meaning different things, and `.ns-adslot`
is a third, older placeholder that `monetization.css` documents as its own
"empty state". Three files, one subject.

**Recommendation:** keep the ad/sponsor split (the reasoning is sound), fold
`.ns-adslot` into `monetization.css` as `.ns-sponsor--empty`, and namespace the
size modifiers so `--leaderboard` means one thing.

### 3.3 🟠 `.ns-lesson` is defined across two stylesheets

- `player.css` — base rule, hover, focus, `[aria-current]`, `[data-state]`
- `lms.css` — `[data-access="members"]` variants

One component, two files, and the filename doesn't predict which. Same story for
`.ns-lesson-nav--thumbs`.

### 3.4 🟡 Domain stylesheets extending core primitives

`lms.css` extends `.ns-card` and `.ns-strip`; `blog.css` extends `.ns-strip`;
`admin.css` defines `.ns-taginput` (a generic form control) — none of which are
theirs. See §5.

### 3.5 🟡 Two brand/foundation specimen folders

`guidelines/` (23 cards) and `brand-content-creation/` (19 cards) use the same
`.card.html` format and are consumed by the same builder, but split on a
distinction ("foundations" vs "brand content") that is not stated anywhere.

## 4. Inconsistencies

### 4.1 🔴 Three taxonomies that don't align

```
CSS files (33)     React folders (14)     Docs families (18)
───────────────    ──────────────────     ──────────────────
lms.css        ┐                          LMS
player.css     ├──►  course/          ┐   Teaching
catalog.css    │     player/          ├─► Training
training.css   ┘                      ┘   CMS
```

- **23 CSS files have no matching React folder**: `a11y ads blog button catalog
  chart code content display form icon lms media monetization motion navbar
  overlay prose table toc training type-fx`
- **4 React folders have no matching CSS file**: `core course forms overlays`
- Docs families invent an 18-name taxonomy that matches neither.

**Consequence:** there is no rule that answers "where does a new component go?"

### 4.2 🟠 React file granularity

`core` and `course` are one-file-per-component. Everything else is
one-file-per-family — `navigation` puts 22 components in 2 files, `ai` puts 25 in
4. So `import { Button } from "…/core/Button.jsx"` but
`import { CourseNav } from "…/navigation/Navbar.jsx"`. Both are defensible; having
both is not.

### 4.3 🟠 Documentation is three formats

1. `.prompt.md` beside the component (34 of 49 have one)
2. An entry in `component-docs.mjs` (138 entries)
3. Long prose headers in the CSS — often the *most* detailed of the three

No component has all three consistently, and there is no rule about which is
canonical.

### 4.4 🟡 Naming

The BEM-ish `.ns-block__element--modifier` scheme is followed almost everywhere.
The inconsistency is in **block naming**: full words (`.ns-lesson`, `.ns-sponsor`,
`.ns-curriculum`) sit beside contractions that need prior knowledge
(`.ns-ccard`, `.ns-chero`, `.ns-thero`, `.ns-tpager`, `.ns-bcard`, `.ns-ltype`,
`.ns-laccess`, `.ns-aiset`, `.ns-tthumb`, `.ns-pframe`).

Also: `.ns-blog-` appears as a class prefix fragment, which looks like a bug.

### 4.5 🟡 Inline styles in templates

99 `style="` attributes across the templates; 14 carry raw values rather than
`var(--token)`. `course-detail.html` alone has 31. Most are legitimate layout
nudges, but there is no stated rule for when an inline style is acceptable, and
`check-components.mjs` enforces exactly such a rule for `.jsx` — the templates
are exempt for no documented reason.

## 5. Layering problems

### Should be lifted OUT of a domain into core

| Currently in | Item | Belongs in |
|---|---|---|
| `player.css` | `.ns-lesson`, `.ns-lesson-nav` (the row and its prev/next) | `lms.css` — it is the LMS row, used by curriculum, rail, and panel |
| `admin.css` | `.ns-taginput` (+2) | `form.css` — a generic tag input |
| `lms.css` | `.ns-card` extensions | `display.css` or a documented extension point |
| `blog.css` + `lms.css` | `.ns-strip` extensions | `display.css` |
| `catalog.css` | `.ns-adslot` | `monetization.css` |
| `ai.css` | `.ns-usermenu` reference | `navbar.css` owns it |

### Genuinely domain-specific and correctly placed

`training.css` (module/path/tier/roadmap), `deck.css` (slides),
`helpdesk.css` (tickets), `auth.css`, `admin.css` (builder/publishbar),
most of `ai.css`, most of `lms.css`.

### The structural gap

There is **no `primitives` layer**. `button.css` and `display.css` are primitives
sitting in the same flat list as `training.css`, so nothing expresses that one
may depend on the other but not the reverse. `check-cascade.mjs` enforces
*layer order*; nothing enforces *dependency direction*.

## 7. Coverage gaps

### 7.1 Missing typings and prompts

**No `.d.ts` (4):** `admin/Admin.jsx`, `admin/Builder.jsx`, `core/Icon.jsx`,
`sections/Sections.jsx` — `Admin` and `Sections` export 17 and 10 components
respectively, entirely untyped.

**No `.prompt.md` (14):** `Admin` `Builder` `Auth` `Icon` `ThemeToggle` `Sponsor`
`Feedback` `Form` `Helpdesk` `Navbar` `Navigation` `Overlay` `Progress` `Sections`.

### 7.2 🔴 Icon subset is 37 glyphs short

`icons/phosphor.css` is a generated subset of 132 glyphs. **37 `ph-*` names used
in markup have no glyph** — including `ph-check`, `ph-sun`, `ph-moon`,
`ph-gear`, `ph-caret-left`, `ph-plus`.

A missing glyph renders as *empty space* — not a fallback, not a box. Every one
is an invisible control. `scripts/check-icons.mjs` now reports them but is
deliberately non-fatal, because **the regenerator named in the file's own header
(`scripts/subset-icons.py`) is not in the repo.**

**This is the highest-severity functional bug in the system and it is blocked on
a missing file.**

### 7.3 No primitive gaps found

Button, Input, Select, Checkbox, Radio, Switch, Badge, Tag, Chip, Card, Avatar,
Table, Tooltip, Modal, Drawer, Popover, Menu, Tabs, Accordion, Breadcrumb,
Pagination, Progress, Spinner, Skeleton, Toast, Alert are all present.

### 7.4 Checks that exist vs. checks that are missing

**Present (6):** tokens, principles lint (no raw colour/radius/z/timing/font/
spacing in CSS), cascade layer order, JSX parse + no-inline-styling, palette
contrast/CVD, markup↔CSS agreement, link integrity, icon subset.

**Missing:**
- No check that a template's markup matches its docs entry (issue #1)
- No dependency-direction rule (domain must not be imported by core)
- No naming lint (`.ns-ccard` vs `.ns-course-card`)
- No duplicate-component detection
- No check that a `.jsx` has a `.d.ts` and a `.prompt.md`
- Templates are exempt from the inline-style rule that `.jsx` must obey

## Blockers before Phase 3

1. **62 uncommitted files** in the working tree. These should be committed or
   stashed on `main` before a reorganization branch is cut, or the diff for each
   batch will be unreviewable. **Needs your decision.**
2. **`scripts/subset-icons.py` is missing.** Without it (or the full Phosphor
   woff2) the 37 missing glyphs can only be fixed by remapping names one at a
   time to glyphs that happen to exist. **Do you have the original script?**
3. **`preview/`, `_site/` and `dist/` are generated but committed.** Every batch
   will produce large mechanical diffs in them. Recommend `.gitignore`-ing
   `preview/` and `_site/` and keeping only `dist/` (it is the published
   artifact). **Needs your call — this changes what consumers can rely on.**

## Decisions I need from you before Phase 2

| # | Question | Options |
|---|---|---|
| A | **Docs source of truth** | (i) Docs generator reads `templates/` — kills the duplication but is the larger refactor. (ii) Keep both, add a check that fails when they diverge — cheaper, keeps two copies. *I recommend (i).* |
| B | **React file granularity** | One file per component (like `core`) or one per family (like `navigation`)? *I recommend one per component; it makes import paths guessable and tree-shaking honest.* |
| C | **Canonical doc format** | `.prompt.md` beside the component, the `component-docs.mjs` entry, or the CSS header? *I recommend the CSS header stays the design rationale, `component-docs.mjs` stays the rendered docs, and `.prompt.md` becomes mandatory and generated from the other two.* |
| D | **Terse block names** | Rename `.ns-ccard`→`.ns-course-card` etc. with aliases, or leave and just document? *Renaming touches a lot of markup for readability alone.* |
| E | **Dead code** | Delete the 171 classes / 28 templates, or first triage which are unfinished features worth wiring up (`.ns-gate`, `.ns-calendar`)? *I recommend triage first — deleting a paywall someone half-built is worse than documenting it.* |
| F | **Domain taxonomy** | Introduce an explicit `foundations / primitives / components / patterns / domains` split in `components/css/`, or keep the flat list and encode layering in `index.css` order + a lint rule? *Flat + lint is far less churn.* |

## What I am NOT proposing

- No redesign. Nothing in this report changes how anything looks.
- No new components. The primitive coverage is complete.
- No token changes. That layer is the healthiest part of the system.
- No rewrite of the check scripts. They are good; they need three more checks.

## Appendix A — how the numbers were produced

| Claim | Method |
|---|---|
| Class counts per stylesheet | `grep -o '^\s*\.ns-[a-z0-9_-]*'` per file, unique |
| Duplicate rule heads | Python: regex rule-heads per file, comment-stripped, grouped by class |
| Template↔docs overlap | Python: template lines >70 chars starting `<`, tested for verbatim presence in `component-docs.mjs` |
| Dead classes | All `.ns-*` in `components/css/` + `patterns/` minus all `class=`/`className=` values in templates, scripts, jsx, cards; JS-applied utilities excluded |
| Orphan templates | Filename absent from both `build-preview.mjs` and `component-docs.mjs` |
| Missing glyphs | `scripts/check-icons.mjs` |
| Token counts | `tokens/tokens.json`, `$value` occurrences per top-level group |
